### 2B. Critical Quality Issues Found

#### CRITICAL BUG: design_review_node Field Name Mismatch
**File:** `agent/nodes/design_review.py:52-56, 61`

```python
# Line 53: Wrong field name — components have "id_str", not "name"
name = comp.get("name", "?")  # Always returns "?"

# Line 54: Wrong field name — components have "description", not "value"
value = comp.get("value", "?")  # Always returns "?"

# Line 61: Wrong field name — nets have "net", not "name"
net.get('name', '?')  # Always returns "?"
```

**Impact:** The design review LLM receives `U1: ? (?) [?]` for every component and `?: U1:3, U2:5` for every net. The entire review is operating blind. This is a **correctness bug**, not just a quality issue.

#### CRITICAL: trace_constraints Never Consumed
**File:** `agent/nodes/netlist.py:440` (written) → `agent/nodes/routing.py:75-315` (never read)

The LLM spends computation computing trace widths and impedance constraints. They're stored in state. Routing_node never reads them. All wires get default 0.254mm width. USB D+/D- nets that need 90-ohm impedance are treated identically to GPIO signals.

#### CRITICAL: Stale Knowledge Database
**File:** `agent/nodes/netlist.py:80-91`

`_load_knowledge_db()` reads from a **static file on disk** (`netlist-preprocessing-experiment/knowledge_db.json`), NOT from `state["knowledge_db"]` which dispatch_node builds live. Components discovered during this run may lack structured knowledge.

#### HIGH: validate_node Missing Wiring Context
**File:** `agent/nodes/validate.py:594` vs `agent/builder.py:78`

Validate runs BEFORE netlist generation. The LLM has zero information about how pins will be connected. It cannot detect pin count exhaustion, bus conflicts, or missing pull-ups.

#### HIGH: placement_node Missing Physical Dimensions
**File:** `agent/nodes/placement.py:34-40`, `agent/placement/blocks_v2.py:28-36`

No footprint pad dimensions, component bounding boxes, or physical sizes. BlocksV2Placer uses hardcoded constants: `GRID_SIZE=1.27`, `BBOX_PAD=1.5`. A 50-pin QFN and a 3-pin SOT-23 get identical treatment.

#### MODERATE: reranker Missing Cross-Component Context
**File:** `agent/reranker.py:254-258`

`existing_str` only shows `ref_des`, `id_str`, truncated description. No pin_summary, footprint, or bus capabilities. The LLM cannot verify cross-component compatibility.

#### MODERATE: Research Summary Truncation
**File:** `agent/nodes/netlist.py:150, 163, 173`

Datasheet info truncated to 300-400 chars. A complex USB-C PD controller's pin-function details get cut mid-sentence.

## 5. Memory Hierarchy Model

### Current State (Flat)

```
Level 0: LLM scratchpad (within single call)
Level 1: AgentState (48-field TypedDict, per-run)
Level 2: ChatSession (in-memory dict, 1hr TTL)
Level 3: DesignSession (in-memory dict, server lifetime)
Level 4: (nothing)
Level 5: (nothing)
Level 6: (nothing)
```

### Proposed Hierarchy

```
Level 0: Scratchpad
  Per-node working memory. Ephemeral. Lost after node returns.
  Current: N/A (nodes return dicts directly)
  Proposed: Internal node state for intermediate computations

Level 1: Current Node Context
  What this node needs to do its job. Subset of AgentState.
  Current: Full 48-field TypedDict
  Proposed: Per-node Context View (see R4)

Level 2: Current Design
  The evolving design across all nodes in one run.
  Current: AgentState (grows from 1 to 27+ active fields)
  Proposed: SynthesisGraph as primary + minimal flat fields for layout/PCB

Level 3: Current Project
  Cross-run memory for this design project.
  Current: DesignSession (last_design, wire_bender_layout)
  Proposed: Design history (decisions, rationale, user corrections)

Level 4: Component Library
  Persistent knowledge about components, pin roles, interfaces.
  Current: KiCad RAG (SQLite), knowledge_db.json (stale file), DEVICE_KNOWLEDGE (hardcoded)
  Proposed: Unified component knowledge graph with freshness tracking

Level 5: Design Knowledge Graph
  Patterns, rules, constraints learned from past designs.
  Current: BUILTIN_TOPOLOGIES (5 rules), _NET_CRITICALITY (hardcoded)
  Proposed: Learned topology rules, failure patterns, design heuristics

Level 6: User Memory
  Cross-session user preferences and patterns.
  Current: ChatSession.preferences (behind feature flag, not active)
  Proposed: Active user memory with preference learning
```

### Information Loss Points

| Where | What's Lost | Level Impact |
|---|---|---|
| After validate completes | `analysis` (subsystem breakdown) | L2 → lost |
| After select completes | `research_results` (candidate details) | L2 → lost |
| After netlist completes | `web_research_results`, `datasheet_search_results` | L2 → lost |
| After routing completes | `_validation_issues` | L2 → lost |
| After server restart | Everything | L2, L3 → lost |
| After 1 hour | ChatSession | L3 → lost |
| Across sessions | All learning | L5, L6 → never existed |

## 6. Retrieval Architecture Analysis

### Current Pipeline

```
User Request → prompt_router (classify) → AgentGraph (48-field state) → Output
```

No retrieval. No ranking. No compression. No validation. The agent is stateless between runs.

### Proposed Retrieval Pipeline

```
User Goal
    │
    ▼
Intent Detection (prompt_router — already exists)
    │
    ▼
┌─────────────────────────────────────┐
│  Context Engine                      │
│                                      │
│  1. Query Formation                  │
│     Extract: components, subsystems, │
│     constraints, intent keywords     │
│                                      │
│  2. Retrieval                        │
│     ├── Design History (Level 3)     │
│     │   Past decisions, corrections  │
│     ├── Component Library (Level 4)  │
│     │   KiCad RAG + knowledge DB     │
│     ├── Design Patterns (Level 5)    │
│     │   Topology rules, heuristics   │
│     └── User Preferences (Level 6)   │
│         Preferred parts, style       │
│                                      │
│  3. Ranking                          │
│     Per item: importance, freshness, │
│     confidence, source, token_cost   │
│                                      │
│  4. Compression                      │
│     Summarize research results       │
│     before injection into prompts    │
│                                      │
│  5. Validation                       │
│     Check for contradictions,        │
│     stale data, missing context      │
│                                      │
│  6. Assembly                         │
│     Build per-node Context Views     │
│     from ranked, compressed items    │
└─────────────────────────────────────┘
    │
    ▼
Context Views (per-node subsets)
    │
    ├──→ analyze_context
    ├──→ research_context
    ├──→ select_context
    ├──→ validate_context
    ├──→ netlist_context
    ├──→ placement_context
    ├──→ routing_context
    └──→ review_context
    │
    ▼
LangGraph Nodes (each receives only its Context View)
    │
    ▼
Output
```

### Context Ranking Framework

Every context item should carry metadata:

| Attribute | Description | Example |
|---|---|---|
| **Importance** | How critical is this for the current node? | `pin_matrix` for netlist: 0.95 |
| **Freshness** | When was this data last updated? | `knowledge_db.json`: stale (file-based) |
| **Confidence** | How reliable is this source? | Web research: 0.6, datasheet: 0.9 |
| **Source** | Where did this come from? | RAG search, web fetch, user input |
| **Token Cost** | How many tokens to include? | `research_results`: ~2,000 tokens |
| **Dependencies** | What other items does this depend on? | `nets` depends on `netlist` |

## 7. Knowledge Graph Analysis

### What Already Exists

The codebase contains a **fully-formed knowledge graph** in `agent/synthesis/graph.py`:

**Entity Types:**
- `ComponentNode` — ref_des, id_str, library, category, pins, metadata
- `PinNode` — key, role (40+ values via PinRole enum), name, etype, voltage_domain
- `NetNode` — name, role (10 values via NetRole enum), pins
- `ConstraintEdge` — type (9 values: SERIES, PARALLEL, POWERED_BY, PULLED_UP, DECOUPLES, etc.)

**Classification Enums:**
- `PinRole` — 40+ values: POWER_IN, GND, SDA, SCL, TX, RX, EN, FB, BOOT, etc.
- `NetRole` — 10 values: POWER, GROUND, SIGNAL, ANALOG, CLOCK, BUS, DIFFERENTIAL, etc.
- `ConstraintType` — 9 topology relationship types

**Topology Rules:**
- `BUILTIN_TOPOLOGIES` — 5 rules: indicator_led, bypass_capacitor, pull_up_resistor, pull_down_resistor, linear_regulator
- Pattern matching via `match_and_constrain()` — graph rewriting system

### The Duplication Problem

`AgentState` carries flat fields that **duplicate** what the graph already models:

| Flat Field | Graph Equivalent | Redundancy |
|---|---|---|
| `pin_matrix` | `ComponentNode.pins` | 100% — built from same data |
| `netlist` | `NetNode.pins` + `import_llm_nets()` | Reconstructed at graph build |
| `nets` | `SynthesisGraph.nets` | Direct 1:1 |
| `power_pins` | `SynthesisGraph.power_pins` | Direct 1:1 |
| `selected_components` | `SynthesisGraph.components` | Direct 1:1 |
| `knowledge_db` | `ComponentNode.metadata["knowledge"]` | Could be merged |

**10 fields could be eliminated** by fully adopting the graph. The `SYNTHESIS_GRAPH_EARLY` and `VALIDATION_DETERMINISTIC` feature flags indicate an ongoing migration that was never completed.

### Evolution Path

```
Current: AgentState (flat dict) + SynthesisGraph (underused)
    │
    ▼
Phase 1: Make SynthesisGraph the primary data model
    ├── Route all nodes through graph queries
    ├── Eliminate redundant flat fields
    └── Keep flat fields only for layout/PCB (separate concern)
    │
    ▼
Phase 2: Add query API over graph
    ├── get_component(ref_des) → ComponentNode
    ├── get_net(name) → NetNode
    ├── get_pins_with_role(role) → List[PinNode]
    └── get_constraints_between(pin_a, pin_b) → List[ConstraintEdge]
    │
    ▼
Phase 3: Context Engine queries graph
    ├── Per-node context assembled from graph queries
    ├── Ranking by relevance to current task
    └── Compression before LLM injection
```

## Biggest Architectural Insight

The codebase already contains a **knowledge graph** (`SynthesisGraph`) with typed entities, relationships, classification enums, and topology rules. It was designed to be the primary data model but was never fully adopted — the `SYNTHESIS_GRAPH_EARLY` flag is still OFF by default.

The real architectural evolution isn't "replace AgentState with something new." It's:

1. **Complete the existing migration** to SynthesisGraph as primary data model
2. **Build a Context Engine** that queries the graph per-node
3. **Add memory hierarchy** on top of the graph for cross-session learning

The graph already models components, pins, nets, constraints, and knowledge. The flat fields in AgentState are legacy artifacts. Finishing what was started is higher-leverage than building something new.

```
Current:
  User → AgentState (48 fields) → All Nodes → Output
                    ↓
           SynthesisGraph (underused)

Proposed:
  User → Context Engine → Graph Queries → Context Views → Nodes → Output
                    ↓                    ↓
           SynthesisGraph          Memory Hierarchy
           (primary model)         (cross-session)
```
